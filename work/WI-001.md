# WI-001 — SMOKE-001 Minimal Collaboration Workflow Verification

- Status: `FIX_REQUIRED` — Technical Review `audits/technical/TR-001.md`: `FIX`; versioned Red Team recheck `audits/redteam/RT-001.md` leaves F1–F3 `MAJOR` and F4 `MINOR` open
- Owner Role: Executor
- Coordinator / Reviewer Role: Technical Lead
- Related Goal: Current `NEXT_ACTION.md` goal (supporting workflow check only; this WI does not satisfy any material-inventory acceptance criterion)
- Work Type: Process smoke test; not modeling and not an experiment

## Objective

Verify the smallest repository collaboration loop: a Technical Lead issues a bounded WI, an Executor produces one harmless evidence artifact within that scope, and the Technical Lead can review the exact artifact and recorded checks.

## Inputs

- `AGENTS.md`
- `docs/roles/executor.md`
- `docs/roles/tech_lead.md`
- `STATUS.md`
- `NEXT_ACTION.md`
- This Work Item

## Allowed Scope

- Read the listed inputs.
- Create exactly one execution artifact: `evidence/smoke/SMOKE-001.md`.
- In that artifact, record:
  - Work Item ID and smoke-test name;
  - execution date and Executor role;
  - reviewed commit (`git rev-parse HEAD`) and pre-existing worktree state (`git status --short`), without modifying or discarding unrelated changes;
  - the exact verification commands run and their actual outputs or exit statuses;
  - a short statement that no modeling, experiment, rule interpretation, data analysis, or formal-result work was performed.
- Run only these repository-local, non-mutating checks after creating the artifact:
  - confirm `evidence/smoke/SMOKE-001.md` exists;
  - confirm it contains `WI-001`, `SMOKE-001`, and the no-modeling/no-experiment statement;
  - run `git diff --check -- evidence/smoke/SMOKE-001.md`.
- The Technical Lead may subsequently create a technical review record under `audits/technical/` for this WI; that review is not part of the Executor-owned write scope.

## Forbidden Scope

- Do not interpret the problem statement, attachments, simulator, rules, objectives, constraints, or data.
- Do not create or modify `ASSUMPTIONS.md`, `DECISIONS.md`, `MODEL_SPEC.md`, `modeling/`, `experiments/`, `results/`, `paper/`, `problem/`, `STATUS.md`, or `NEXT_ACTION.md`.
- Do not create an EXP specification, run a candidate or formal experiment, execute the simulator, fit a model, calculate competition metrics, or promote any result.
- Do not alter official-material candidates or claim that any material is verified.
- Do not commit, branch, merge, push, install dependencies, access the network, or delete/overwrite pre-existing files.
- Do not edit this WI or expand its scope during execution.

## Required Outputs

- Executor: `evidence/smoke/SMOKE-001.md` containing the required trace and actual check results.
- Technical Lead after execution: a separate technical review disposition (`PASS`, `FIX`, or `ESCALATE`) using `audits/technical/TR-TEMPLATE.md`.

## Acceptance Criteria

- The sole Executor-created file is `evidence/smoke/SMOKE-001.md`.
- The artifact contains every record required by Allowed Scope and reports actual observations without fabricated success.
- All three permitted checks complete and their results are recorded.
- The diff contains no content outside the authorized smoke artifact, excluding unrelated pre-existing user changes documented in the artifact.
- No modeling, rule/data interpretation, EXP work, simulator run, metric computation, or formal-result activity occurs.
- Technical Review can identify the reviewed commit, artifact, commands, results, and any limitations from the evidence artifact alone.

## Stop Conditions

- Stop after the evidence artifact and permitted checks are complete; do not begin follow-on work.
- Stop without attempting repair if a required input is missing, the target artifact already exists, or the worktree contains an overlapping change to the target path.
- Preserve and report any failed check exactly as observed.

## Escalation Conditions

- Escalate to the Technical Lead if any required action would exceed Allowed Scope, touch a forbidden path, mutate pre-existing work, or require an additional tool/dependency.
- Escalate contradictory repository instructions or ambiguous ownership to the Technical Lead.
- Any request to begin modeling, interpret rules/data, create or run an experiment, or change the current integration goal requires a new or revised authorized WI and, where applicable, Strategist approval.

## Completion Boundary

Execution of this WI proves only that the bounded handoff-and-review workflow can produce traceable repository evidence. It provides no evidence about competition rules, data, model validity, simulator correctness, solution quality, or readiness for formal work.
